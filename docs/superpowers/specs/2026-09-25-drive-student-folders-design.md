# Lessons in Google Drive, per student

Todoist 6hRQQVWxcCgrjRCq. A lesson prepared on the site appears in the
student's place in Drive. A supported edit made in Drive comes back to the
lesson, without manual upload, duplicates or a silent overwrite. Drive is
never the database of student details, permissions or payments.

## 1. What is true

- The app already holds a Drive login for **mea.beclick@gmail.com**
  (`GOOGLE_OAUTH_*`, scope `drive.file`) that the nightly backups use
  (`server/drive/client.mjs`). `drive.file` reaches files the app created,
  including other people's edits to them, and nothing else.
- Probed on production, 2026-09-25, with a document created and then
  trashed:
  - **HTML import** with `dir="rtl"` makes a real Google Doc with
    right-to-left paragraphs.
  - Updating the same file in place works.
  - **Markdown export** returns the structure with regular noise: headings
    wrapped in `**…**`, list items as `> * item`, `\=` escapes, and
    trailing double spaces.
- A lesson's structured content is its `plan` versions (#79, #131). The
  student sees the published `slides`.

## 2. Decisions

**D1. Structure** (chosen by Lior, 2026-09-25): an app-owned root folder
«מאה בקליק — תלמידים», then **a folder per student** «<name> · <code>».
Each student folder holds **a document per lesson** and **an index
document** «<name> — כל השיעורים» that links to every lesson document,
newest first. The index is regenerated by the app and says so on its first
line; edits to it are not synced.

**D2. Format.** Written as HTML (`dir="rtl"`) from the published plan:
title, one heading per slide with its bullets and note, then each worked
example as «דוגמה: <problem>» with numbered steps and «תשובה: …». Read
back as Markdown export, through a tolerant parser (§3).

**D3. One idempotent job, every 10 minutes.** `syncDrive()` walks every
student's generated lessons (`lessonsForStudent`) and, for each:
- no document yet → create it (and the folders on the way), record its id
- the site has published a newer plan than the document holds, and Drive
  is unchanged since the last sync → update the document
- **Drive changed since the last sync → pull**: parse the document, save
  it as a **draft** plan version (never published), and WhatsApp the tutor
  with the editor link. The site's newer version, if any, is **not** pushed
  over her Drive edit. That is the "no silent overwrite" rule.
- the document was trashed or deleted → recreate it from the published
  plan, and tell her
It then regenerates each index whose lesson set changed. The target
latency is documented as "within 10 minutes". A 10-minute systemd timer
calls `GET /api/drive-sync` with the cron key, like the other timers.

**D3a. Found by the real-Drive proof and the final review** (added after
implementation):
- **"Edited in Drive" is decided by content.** Google moves a new
  document's `modifiedTime` again seconds after our write. So a moved time
  means: export, and compare against the hash of the export taken right
  after our last write or read (`synced_hash`, migration 020). If the hash
  differs but the content still parses to exactly the version we wrote,
  that's still not her edit (an export taken before Google settled).
- **An edit that cannot be read blocks the file** (`blocked`). Her text is
  the only copy, so nothing is pushed over it until it parses or the file
  is replaced. She is told once.
- **After a pull, the new draft counts as the synced version.** So a later
  Google touch compares equal, and only a *later* publish is pushed.
- **Only unambiguous lessons are copied.** A lesson is linked to a student
  only by the booking's start time. It is copied only if exactly one
  student has a live booking at that time, so it never lands in the wrong
  family's folder.

**D4. Drive edits go straight to the student** (changed by Lior,
2026-09-26, "full sync of the lesson to the student"; first built as a
draft). The edit is published as plan *and* deck, the same way the editor's
«פרסום» does it (`publishPlan`), and she is told with a link to the editor,
where earlier versions can be restored. Two guards keep it safe:
- **Quiet period.** Google Docs saves every keystroke, so an edit waits
  until the document has been untouched for 10 minutes. Nobody sees half
  a sentence. It reaches the student about 10–20 minutes after she stops
  typing.
- **An edit that cannot be read** is never published. It blocks the file
  as before.

**Reuse is unaffected.** A lesson is generated for one booking, so its
Drive document is that student's own copy. Sharing across students belongs
to the materials library (2026-09-24 design), keyed by skill. Promoting an
improvement from a student's copy to the library must stay an explicit
action, never a side effect of a sync.

**D5. What is stored.** A new table `drive_items(key, file_id, kind,
synced_version, synced_modified, updated_at)`, with keys `root`,
`student:<id>`, `index:<id>` and `lesson:<slug>`. File ids and sync
bookkeeping only. No student data lives in Drive beyond what the lesson
documents and folder names already say.

**D6. Switched off where it must be.** When `GOOGLE_OAUTH_*` is missing
(tests, the characterization harness, a fresh box) the job reports
`{ skipped: 'not configured' }` and touches nothing. The harness blocks
those variables.

**D7. Lessons without a plan version** (from before #106) are skipped:
there is nothing structured to write.

## 3. The read-back contract

After the Markdown export has been normalized (leading `> ` stripped,
`**…**` around a whole line stripped, `\X` unescaped, whitespace trimmed):
- `# X` → title
- `## דוגמה: X` → a new example with problem X; numbered items `1. X` →
  steps; a line `תשובה: X` → answer
- any other `## X` → a new slide with heading X; items `* X`, `- X` or
  `1. X` → bullets; a line wrapped in `*…*` or `_…_` → the slide's note;
  any other non-empty line → a bullet, so nothing she types is lost
- the index document is never read

The result goes through `normalizeEdit` (#131), so a Drive edit meets the
same rules as an edit in the site's editor. If it fails, nothing is
saved, and she is told why.

## 4. Not in scope

- Files added to a student folder by hand: `drive.file` cannot see them.
  Broader access would need a one-time Google approval from Lior.
- Games and homework in Drive.
- Real-time push notifications from Drive (webhooks). Polling every 10
  minutes meets the target without a public callback URL.
